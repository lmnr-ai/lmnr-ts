# tracing/

## Context / startActiveSpan

- `Laminar.startActiveSpan` activates the span on `LaminarContextManager`'s AsyncLocalStorage stack. Sibling / unrelated async tasks (i.e. callbacks that run outside the returned promise's chain — `setImmediate`, separate timers, independent processor callbacks, etc.) do NOT inherit the activated span — they live in a different ALS frame. For spans that must parent across detached async callbacks, pass `global: true`: the span is pushed onto a process-global stack that `getContext()` falls back to when the ALS stack is empty. The span is popped from that stack automatically in `LaminarSpan.end()`. Use sparingly — it is roughly analogous to Python's `context.attach(...)` / `start_as_current_span` global activation.
- If you pass `context: ...` into `startSpan` / `startActiveSpan` it replaces the usual `LaminarContextManager.getContext()` base — so if you need the global fallback, build your context on top of `LaminarContextManager.getContext()` rather than on `otelContext.active()`.
- `LaminarSpan.end()` only calls `popContext()` once (for the activated-span push). Do NOT push additional context frames elsewhere in `_startSpan` without a matching pop — `popContext`'s filter drops _already-ended_ spans by spanId, but a leaked wrapper of a still-live parent span (e.g. `trace.wrapSpanContext(...)` built from `parentSpanContext`) looks "valid" and stays on the stack, growing it unboundedly across repeated start/end pairs. The `parentSpanContext` path is resolved purely via `trace.setSpan(entityContext, ...)` + passing `entityContext` to `getTracer().startSpan(..., entityContext)` — no push needed.

## Span batching / export — byte-size flush trigger

- **`SizeLimitedBatchSpanProcessor` (`packages/lmnr/src/opentelemetry-lib/tracing/batch-processor.ts`) adds a THIRD flush trigger to OTel's two, and it is OPT-IN** via `Laminar.initialize({ flushBySize: true })`. Upstream flushes on `maxExportBatchSize` items OR `scheduledDelayMillis`; neither bounds the payload, so a few large GenAI spans build an export the backend rejects. `maxExportBatchSizeBytes` (default 32 MiB) flushes the buffer when the span being ended *would* push it over. `maxExportBatchSizeBytes` alone does NOT enable it — passing a byte limit must not silently switch transports. `disableBatch` wins over `flushBySize`. Option chain: `Laminar.initialize` → `initializeTracing` → `LaminarSpanProcessor` → the batch processor.
- **This is a cross-language parity SURFACE but deliberately NOT a line-for-line port** — the Python SDK (`src/lmnr/opentelemetry_lib/tracing/batch_processor.py`) needs a dedicated flush thread, a lock around the running byte total, an `os.register_at_fork` handler, an inline-export backpressure fallback, and a "span ≥ half the limit" overshoot rule. **None of that exists here, and adding it would be cargo-culting.** Three measured runtime differences explain why:
  1. **JS `forceFlush()` does not block the caller.** `BatchSpanProcessorBase._flushOneBatch` moves the buffered spans out of `_finishedSpans` synchronously inside the Promise executor and only *awaits* the network. Measured: `span.end()` worst case 0.34ms against a 300ms export. Python's `force_flush` performs the export on the calling thread (load-tested p99 ~664ms), which is the only reason it needs a background thread.
  2. **A tight producer loop stays bounded without backpressure**, because that same synchronous drain happens before the next span arrives. Measured: batches stayed at 25 spans against a 100 KB limit with a 200ms export. Python's async handoff can be outrun (measured 95 MiB exports against a 16 MiB limit), hence its inline fallback.
  3. **`onEnd` calls `super.onEnd(span)` AFTER flushing, so the triggering span is genuinely excluded** from the batch it caused. Python's flush is async, so the trigger always rides along — that is what forces its half-the-limit rule. Here a 0.6x-limit span goes out alone with no such rule; pinned by `excludes the triggering span from the batch it caused` (fails if the flush is moved after the enqueue).
- **The `.catch()` on the `forceFlush()` call is load-bearing, not defensive.** Nothing awaits that promise, and `forceFlush()` REJECTS when an export fails — so without it a failing exporter produces one unhandled rejection per flush, fatal under Node's default `--unhandled-rejections=throw`. Verified: three failing exports → three unhandled rejections. Pinned by `survives an export failure without an unhandled rejection`.
- **Python's "resync the running total when the buffer looks empty" logic is intentionally ABSENT.** A stale total can only cause an *early* flush, and an early flush on an already-drained buffer is a no-op in JS (`_flushOneBatch` returns immediately on an empty buffer — no export, no wire traffic). In Python the same spurious flush is a real blocking round trip on a user thread, which is what makes it load-bearing there. Confirmed by mutation testing: adding the resync changed no observable behavior, so reading upstream's private `_finishedSpans` was dropped rather than kept for symmetry.
- **`utf8Size` uses `Buffer.byteLength`, which is exact — do NOT port Python's strided sampling.** `.length` counts UTF-16 code units and undercounts CJK ~3x / Cyrillic-Arabic ~2x / emoji ~1.4x. Python samples because `len(s.encode())` allocates the whole encoded copy; `Buffer.byteLength` walks the string in native code without allocating, so it is both **cheaper and more accurate** (measured 27us vs 16us on a 20k-char CJK string — but the sampled estimate was *wrong* for emoji by +11.7%, because indexing a JS string splits surrogate pairs and each half encodes as U+FFFD). Exact measurement costs ~76us on a 192 KB span. Pinned by the parametrized `is exact for <script>` cases, which fail on 9 counts if reverted to `.length`.
- **TS's `maxExportBatchSize` default is 512, NOT Python's 64** — and unlike Python (where the 64 was never actually applied because every layer passed `None` through) the TS 512 is real and documented. Deliberately left alone; do not "align" the two without a decision, they are different products' defaults.

## Span payload size limit

- `truncateSpanPayload` + `MAX_MANUAL_SPAN_PAYLOAD_SIZE` (10MB) + `TRUNCATION_SUFFIX` (`...[Laminar: truncated]`) live in `packages/lmnr/src/utils.ts`. Before LAM-2050 the TS SDK had **no span payload limit at all** (only `slicePayload`, which is for eval datapoints), so an oversized manual payload was shipped whole; Python replaced it with a placeholder. Both now truncate at the same boundary with the same suffix — this is a cross-language parity surface, change the two together.
- Two entry points must both truncate: `LaminarSpan.setInput`/`setOutput` (`opentelemetry-lib/tracing/span.ts`) and the `observe()` decorator's `serialize` (`opentelemetry-lib/tracing/decorators.ts`). `serialize` takes a `kind` param purely so the warning names input vs output, and it is injected into `handleStreamResult`, so the streaming output paths inherit truncation for free — do NOT add a separate limit there.
- The string fast-paths bypass `serialize` (`typeof input === 'string' ? input : serialize(input)`), so each needs its own `truncateSpanPayload` call. Missing one is the easy way to reintroduce the bug for string payloads only.
- **`JSON.stringify` is typed `string` but returns `undefined` for a top-level `undefined`, function, or symbol** — so `truncateSpanPayload` carries a `typeof serialized !== "string"` guard and hands those back untouched (`setAttribute` treats them as a no-op, which is what they did before the limit existed). Without it, `.length` threw a `TypeError`: `setInput`/`setOutput` propagated it to the caller, and every void-returning `observe()` logged a spurious "Failed to serialize output" warning (Bugbot caught this on PR #289). Any future call site that feeds `JSON.stringify` output into a string helper needs the same guard. Pinned by `test/span.test.ts` ("does not throw on values JSON.stringify cannot serialize") + `test/observe-decorator.test.ts` ("... returns void").
- Do NOT confuse this with `slicePayload` (same file): that one appends `'...'`, is measured against `INITIAL_EVALUATION_DATAPOINT_MAX_DATA_LENGTH` (16MB), and exists for the evals-client 413-shrink retry — a different limit for a different wire path.

## Release stamp (`packages/lmnr/src/opentelemetry-lib/tracing/release.ts`)

- **`LaminarSpanProcessor.onStart` stamps `lmnr.span.release` (`SPAN_RELEASE`) on EVERY span, next to `lmnr.span.sdk_version`**, not through global metadata. app-server groups an agent's traces into versions by this value (LAM-2414), so a span from a bare OTel tracer (eve's `otelIntegration`, a standalone `new LaminarSpanProcessor()`) needs it too.
- The value is resolved ONCE in the processor constructor by `detectRelease`: `Laminar.initialize({ release })` (threaded through `initializeTracing` → `startTracing` → the processor), then `LMNR_RELEASE`, `GITHUB_SHA`, `SENTRY_RELEASE`, platform commit SHAs, per-deploy ids (`K_REVISION`, `GAE_DEPLOYMENT_ID`, `FLY_IMAGE_REF`), a numbered AWS Lambda version (`function:N`, never `$LATEST`), and finally `.git/HEAD` read from disk (no `git` subprocess; handles packed refs and linked worktrees via `commondir`). **Only add a source whose value changes on every code deploy**: one that survives a deploy merges two agent versions server-side. Trimmed, capped at 128 code points (not UTF-16 units). Truncating a full SHA to 7 chars is app-server's job. This is a **cross-language parity surface** with the Python SDK's `opentelemetry_lib/tracing/release.py`: keep the source list and order identical.
- **When `spanProcessor` is another `LaminarSpanProcessor`, only the OUTER one's `onStart` runs** (it calls the inner one's batch processor directly), so the outer processor takes the inner one's release unless `release` is passed explicitly. Pinned by `keeps the release of a wrapped LaminarSpanProcessor`.
- Every step is wrapped in try/catch (`process` may not exist on edge runtimes, `fs` reads may fail); detection never throws into `initialize()`.
- **The agent sandbox exports `LMNR_RELEASE`**, so a manual `detectRelease()` there returns that value, not this checkout's HEAD. Use `env -u LMNR_RELEASE` to check the git path. `test/release.test.ts` clears every release env var and overrides `process.cwd` to a temp dir per test, and asserts that the temp dir is not inside a git checkout (otherwise the "nothing detected" cases would pick up an ancestor's `.git`). Spans in every other suite carry this checkout's commit (or the sandbox's `LMNR_RELEASE`) as their release.
