# LangSmith bridge (`bridges/langsmith/`, LAM-2590)

`Laminar.initialize({ bridges: ["langsmith"] })` records every run the `langsmith` JS SDK sends as a Laminar span too. Supported: langsmith >= 0.10.0 (`MIN_LANGSMITH_VERSION`; dev pin 0.14.0). The whole suite also passes with 0.10.0 swapped in (`pnpm add -D langsmith@0.10.0`, run `test/langsmith-bridge.test.ts`, restore `package.json` and the lockfile). Older versions have `processRunOperation` but no `_mergeRuntimeEnvAndMaskMetadata`, so `autoBatchTracing: false` runs were missed: copies below the floor are skipped with a warning, and `isAvailable()` is false when no supported copy resolves. A copy with an unknown version is let through. Port of lmnr-python's `opentelemetry_lib/bridges/langsmith/` (read its `AGENTS.md` for the design rationale); keep names, attributes and translation rules in step. The contract shared with the other bridges is in `../AGENTS.md`.

## The tap (`tap.ts`)

- LangSmith isn't OpenTelemetry-based: it sends runs to its REST API (`/runs/multipart`, `/runs/batch`, plain `/runs`). Everything (`traceable`, `wrapOpenAI` / `wrapAnthropic` / `wrapSDK`, LangChain's `LangChainTracer`, LangGraph, hand-built `RunTree`s) ends in `RunTree.postRun()` / `patchRun()` → `Client.createRun` / `updateRun`, which sample (`tracingSamplingRate`), redact (`hideInputs` / `hideOutputs` / `hideMetadata`, `anonymizer`) and then hand the run to `Client.processRunOperation({action, item})`, the batch queue.
- **Tap point: `processRunOperation`**, the JS equivalent of Python's private `_create_run` / `_update_run`: it gets the final, redacted, sampled run. It sets `item.item = mergeRuntimeEnvIntoRun(...)` before its first `await`, so the wrapper calls through first and snapshots `item.item` right after, synchronously, then returns LangSmith's own promise. `feedback` operations are skipped. The snapshot is a shallow copy without `attachments` (file bytes are never copied), JSON round-tripped through Laminar's cycle-safe `toJson`; LangSmith's own object is never mutated (`does not mutate the run LangSmith queues`).
- **`autoBatchTracing: false`** (or a run without `trace_id` / `dotted_order`) sends each run itself. Creates are read from `_mergeRuntimeEnvAndMaskMetadata`'s result (the body it POSTs); updates from `updateRun` after it resolved (it redacts `run` in place), when no `processRunOperation` call happened inside it (an `AsyncLocalStorage` flag). Such an update is recorded only if its create was seen: `_filterForSampling` had side effects in older versions, so the tap can't ask whether an unseen run was sampled out. The traffic test runs both modes.
- **Replicas** (`LANGSMITH_RUNS_ENDPOINTS`, `replicas` on a run / `traceable`): `postRun()` / `patchRun()` call the client once per replica, ids remapped unless `primary` or the run's own project. Wrappers open an `AsyncLocalStorage` scope that collects the writes. The one with the run's own id is dispatched **at once**, not at scope end: `traceable` runs the function while `postRun` still awaits, so children can be posted before the parent's `postRun` resolves, and they must find the parent's node. With no own-id write, the first is dispatched when the scope ends (the dispatch is a reaction registered before the caller's, so it runs before the caller moves on to `patchRun`).
- **Every reachable copy is patched.** langsmith 0.14 ships CJS (`.js`) and ESM (`.mjs`) builds whose `Client` / `RunTree` are distinct classes. `packageFiles` resolves `langsmith` and `langsmith/run_trees` from this SDK, `process.cwd()`, and `@langchain/core`'s location (the copy LangChain's tracer uses), takes the CJS file from `require.resolve` and the ESM file from the package's `exports` map, and loads the ESM ones with `require(esm)` (Node >= 22.12, our `engines` floor). That shares the ESM loader's cache, so an app's `import "langsmith"` (before or after `initialize()`) gets the patched class: checked by hand on the built `dist` in plain Node, static and dynamic imports. **tsx breaks that identity**: its `require` hook compiles the `.mjs` file to CommonJS, so `require(esm)` gets a separate copy and the app's `import` stays unpatched. Before the fix, the docs sample run with `npx tsx` recorded nothing, with no error. So after the synchronous `install`, `installImported()` also loads every file with `import(pathToFileURL(path))`, which goes through the same loader as the app, and patches any new copy (`patch` skips targets that are already ours). It is asynchronous, so a run that starts in the same tick as `Laminar.initialize()` under tsx loses its create. Its update is recorded as a complete run without inputs (JS updates don't repeat them), and its children's paths start at them. Servers aren't affected, and plain `node` (type stripping) isn't either. The public docs have a troubleshooting entry for this. `patches the copy an app's import gets (tsx)` pins it, and fails if `installImported` is a no-op. Check that the CJS `dist` keeps a real `await import(...)` (rolldown leaves a non-literal specifier alone).
- `uninstall` restores each method only if it is still our wrapper; wrappers check `tap.active`, so a wrapper stacked on top of ours just calls through.

## LangChain JS context (`_createRunFor*Start`)

- LangChain JS runs tracer callbacks on a background queue (`LANGCHAIN_CALLBACKS_BACKGROUND`, default on). While the queue is busy, the next run's callbacks (and so `postRun` → `processRunOperation`) run in the async context of an **earlier** call: a chat model invoked under Laminar span B landed under span A from the previous call. Nested runs don't care (their parent run decides), roots do.
- Fix: `CallbackManager.handle*Start` calls `BaseTracer._createRunFor{LLM,ChatModel,Chain,Tool,Retriever}Start(x, y, runId, parentRunId, ...)` synchronously, in the caller's context, before queueing. The tap wraps those on every reachable `@langchain/core/tracers/base` copy (CJS and ESM, as above) and keeps `runId → LaminarContextManager.getContext()` (bounded at 10k, taken on the run's create). `records a LangChain run under the Laminar span it started in` fails without it.
- LangChain only nests a runnable called inside a `RunnableLambda` when its `AsyncLocalStorageProviderSingleton` is initialized (`@langchain/langgraph` does it on import); otherwise each such call is its own root run. That's LangChain's behavior, not the bridge's.

## Runs → spans (`runs.ts`)

Same as Python `runs.py`:

- `onCreate` converts the inputs to attributes at once (`inputAttributes`, `requestAttributes`) and drops them from the stored run; `onUpdate` merges the update (non-null fields win) and emits. A create that already has `end_time` is emitted at once and a later update for it ignored. An update whose create was never seen is recorded as a complete root run (except on the non-batched path, above). Open and finished runs are insertion-ordered `Map`s bounded at 10k; runs that never end are dropped.
- **Ids:** trace id = the LangSmith trace UUID's 32 hex digits; span id = 64-bit FNV-1a (BigInt) of the run UUID's lowercase text, `|| 1`. Cross-language vectors from lmnr-python's `span_id_for` / `trace_id_for` are in `test/langsmith-bridge.test.ts`; regenerate them there if either side changes.
- **Spans:** a real span from Laminar's provider (tracer `langsmith`, version = the patched copy's `package.json` version, also stamped as `lmnr.span.bridge.version`), with the run's ids stamped over the SDK's afterwards as the Mastra exporter / pi-durable do (`Object.assign(span.spanContext(), …)`, `dropPathInfo` of the allocated id, `parentSpanContext` / `parentSpanId`, then `lmnr.span.path` / `ids_path` overwritten with the node's). Started inside `context.with(<Laminar context at create>)`, because `LaminarSpanProcessor.onStart` reads association properties from `context.active()`; the run's attributes are passed as start attributes, so Laminar's own (`observe({ sessionId })`, metadata) are applied after them and win. Errors become an `exception` event plus ERROR status.
- Times: JS `start_time` is an ISO string whose last three microsecond digits are an ordering counter (kept as a sub-millisecond fraction); `end_time` is epoch milliseconds. End is clamped to start.
- Nesting, glue runs (nested `RunnableSequence` / `RunnableLambda` and `langsmith:hidden` runs, e.g. LangGraph's `__start__`), distributed parents and parent paths: as in Python.

## Translation (`translate.ts`)

Port of Python `translate.py`, reusing the Langfuse bridge's `normalizeMessages`, `requestParameterAttributes` (extracted from `modelParameterAttributes` for this) and `LS_PROVIDER_ALIASES`, and the LangChain instrumentation's `smallState`. JS-specific additions:

- LangChain JS serializes a `HumanMessage` without `type` in `kwargs`; the class name (`id[-1]`) decides the role.
- Internal metadata also drops `versions` (LangChain JS's package versions); `ls_invocation_params`, `ls_integration` and the like go by the `ls_` prefix. LangChain JS copies `model` / `stream` from invocation params into metadata; dropped on the root by the same equality check as Python (compared as JSON).
- Usage also reads LangChain JS's `llmOutput.tokenUsage` (`promptTokens`, camelCase). The response id falls back to the AI message's own id (LangChain JS keeps the provider's `chatcmpl-…` there, not in `response_metadata`), unless it is one of LangChain's `run-…` ids.
- A JS error string is `Error: message`; it parses to type `Error` and the message.

## Bridge (`index.ts`)

- `conflictingInstrumentations`: `OpenAI`, `anthropic`, `cohere`, `google_genai`, `google_aiplatform`, `openrouter`, `langchain`, `openAIAgents`, `claudeAgentSDK` (LangSmith has `wrapClaudeAgentSDK` and an OpenAI Agents processor). Python's set minus the instruments TS doesn't have; `piDurable` stays on. Unlike `LLM_INSTRUMENTATIONS`, Claude Agent SDK is included.
- `inheritsGlobalContext: false`. There is no private-provider flag in TS: Laminar never registers its provider globally (it sets only the context manager when none is set), so LangSmith's OTel mode (`LANGSMITH_TRACING_MODE`, legacy `LANGSMITH_OTEL_ENABLED`), which exports through the global provider, can't pick up Laminar's. Python needs `requires_private_tracer_provider` because there Laminar may own the global provider. Runs are bridged in that mode too: they still go through `processRunOperation`, and only the queue's drain hands them to LangSmith's OTel translator.
- `isAvailable()` is false when no supported `langsmith` copy with a `Client` resolves; `install` warns per copy below the floor or without `processRunOperation`.

## Known gaps

- **No LangGraph topology.** In TS it is published by the LangChain instrumentation (Pregel `_streamIterator` patch + `handler.takeTopology()`), which the bridge has to disable; Python keeps it through its separate LangGraph instrument.
- **Bundled apps** (esbuild / Next.js server bundles where `langsmith` is inlined and not resolvable from `node_modules`): nothing is patched. The Langfuse bridge avoids this through a global slot; LangSmith has none.
- Laminar spans created _inside_ a run nest under the nearest Laminar span, not under the run (the run's span exists only once it ended); distributed traces whose upstream root ran under a Laminar span split into two Laminar traces; as in Python.
- On the non-batched path an update whose create came before `initialize()` is dropped.
- Under tsx, a run started in the same tick as `initialize()` has no inputs (see the tap section).
- The trace id debug mode records for a root run (`recordDebugTraceId`) is the SDK-allocated one, read before the run's id is stamped over it (same as pi-durable roots).

## Tests (`test/langsmith-bridge.test.ts`)

- `test/langsmith-bridge/fixtures/js-sdk-payloads.json`: what langsmith 0.14.0 handed to `Client.createRun` / `updateRun` (`traceable` nesting and errors, `wrapOpenAI` tool loop and stream, LangChain `ChatOpenAI` with tools, LangGraph). Recorded at the public methods, so before redaction and runtime merging; replayed through the recorder as `{...run, id: runId}` for updates. Re-record with `npx tsx test/langsmith-bridge/fixtures/record.ts` (providers and LangSmith mocked, no keys), then `biome check --write` it.
- Live tests use a real `Client` whose `fetchImplementation` records LangSmith's requests (multipart bodies parsed with `Response.formData()`); `traceable` gets `tracingEnabled: true` and LangChain an explicit `LangChainTracer({ client })`, so nothing reads `LANGSMITH_*` env or reaches the network. The traffic test compares LangSmith's requests with and without the bridge (ids and times normalized) in both batching modes; keep it passing.
