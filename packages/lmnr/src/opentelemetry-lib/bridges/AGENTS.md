# bridges/ — `Laminar.initialize({ bridges: [...] })` (LAM-2500)

## Shape

- **Terminology:** call the bridged SDK the "source SDK" ("third-party tracing SDK" in public docs), never a "competitor". Future bridges need not be competing products, and the word spreads from here into other code and docs. Same in lmnr-python.
- `types.ts`: `LaminarBridge` (public union, `"langfuse"` today), the `Bridge` interface (`name`, `conflictingInstrumentations`, `inheritsGlobalContext`, `isAvailable()`, `install(ctx)`, `uninstall()`, optional `onFlush()`), and `LLM_INSTRUMENTATIONS`. The interface assumes nothing about how a bridge hooks its SDK: Langfuse hands span copies to `ctx.spanProcessor`; a network-level bridge (LangSmith, Braintrust) would build spans with Laminar's `getTracer()` and set `inheritsGlobalContext: false`. lmnr-python's `LaminarBridge` / `BridgeContext` is the same contract (Python also has `requires_private_tracer_provider`, since there Laminar and Langfuse would otherwise share the global provider). `index.ts`: the name → factory registry plus `resolveBridges` / `installBridges` / `uninstallBridges` / `flushBridges`. A new bridge (LangSmith, Braintrust, ...) adds its name to the union and one registry entry. Nothing else in `laminar.ts` changes.
- `Laminar.initialize` calls `resolveBridges` before tracing starts, so an unavailable bridge never disables anything (Langfuse: only when its slot has an unexpected shape, since the SDK's presence can't be detected without loading it). Then, only when the user passed no `instrumentModules`, it sends the union of `conflictingInstrumentations` down as `InitializeOptions.disabledInstrumentations` → `initInstrumentations`, which wraps every auto-instrumentation in `enabled("<instrumentModules key>")`. With explicit `instrumentModules` nothing is disabled and `warnAboutOverlaps` logs instead. An installed bridge with `inheritsGlobalContext` (Langfuse; OpenTelemetry-based SDKs only) also turns on `inheritGlobalContext`; an unknown or unavailable name must not (Bugbot on #361). `shutdown()` turns it back off, but only if the bridge turned it on. Bridges are installed after `initializeTracing` with `getSpanProcessor()` and uninstalled in `shutdown()` after the flush.
- `LLM_INSTRUMENTATIONS` is all LLM-provider and framework instrumentations, minus Claude Agent SDK, OpenCode and TypeSafe (no bridged SDK covers them, so nothing is recorded twice; Laminar also instruments the agent SDKs better). Keep the list in step with lmnr-python's `LangfuseBridge.conflicting_instruments`. Non-LLM ones (browsers, kernel, Temporal) stay on. When you add a new auto-instrumentation, give it an `enabled(...)` guard, and add its key here if it emits LLM spans.

## Langfuse (`langfuse/`)

- **Hook point:** `@langfuse/tracing` 4.x–6.x reads its tracer from `globalThis[Symbol.for("langfuse")].isolatedTracerProvider`, which `setLangfuseTracerProvider` writes, and falls back to the global provider. Every span from `observe` / `startActiveObservation` / `@langfuse/openai` / `@langfuse/langchain` uses tracer `langfuse-sdk`. Every copy of the package (CJS, ESM, duplicates, bundled) shares that slot.
- **The bridge never loads `@langfuse/tracing`** and reads no `package.json`. Resolving the package from the SDK or `process.cwd()` failed in bundled apps (Next.js server bundles, esbuild Lambdas, `bun build --compile`): the bridge logged "not installed" and stayed off although the slot would have worked. Verified with an esbuild bundle run outside any `node_modules`: the old code mirrored nothing, the new one does. If the slot doesn't exist yet, `langfuseState()` creates it exactly as Langfuse's `getGlobalState()` does (locked `defineProperty`, `{ isolatedTracerProvider: null }`), and Langfuse reuses an existing slot, so `Laminar.initialize()` may run before Langfuse loads (`test/langfuse-bridge-init-order.test.ts`). Cost: a missing Langfuse can't be detected, so `isAvailable()` is false only when the slot isn't a configurable data property (Langfuse internals changed); otherwise the bridge installs and simply never sees a span.
- **Never add `LaminarSpanProcessor` to the customer's provider.** Its `onStart` writes `lmnr.*` attributes onto the span, and those leak into Langfuse's export. The bridge instead runs `onStart` on a shadow (`Object.create(span)` with its own attribute bag), wraps `span.end` with a non-enumerable own property, and after the real end hands `onEnd` a copy (`Object.create(span)` with merged attributes and maybe a synthesized `exception` event). `test/langfuse-bridge.test.ts` "leaves Langfuse's export identical" fails if the real span is passed to `onStart`.
- **The wrapper resolves the inner provider on every `getTracer`.** `inner == null` means the global provider, read through Laminar's `@opentelemetry/api` (the app's copy, see the package `AGENTS.md`), so an OTel SDK started after `Laminar.initialize()` still works. `startActiveSpan` keeps the caller's arity and only wraps the callback, so the inner tracer still parents and activates the span. Non-recording spans (no provider, or sampled out) are not mirrored.
- **Self-healing:** `install` replaces the `isolatedTracerProvider` data property with a getter/setter. A later `setLangfuseTracerProvider(p)` from the app becomes the new inner provider, and the getter keeps returning the wrapper. `uninstall` restores a plain data property holding the app's latest provider (the slot itself is locked on `globalThis` and stays).
- **Translation (`translate.ts`, port of lmnr-python's langfuse `_translate`):** Langfuse's integrations report `input` / `output` without their `input_*` / `output_*` details (prompt 11 with 2 cached becomes `input: 9, input_cached_tokens: 2`), so every detail key is added back. Laminar's backend wants totals and subtracts cache itself. Emit the semconv keys `gen_ai.usage.cache_read.input_tokens`, `cache_write.input_tokens` and `reasoning.output_tokens`, not the legacy `cache_read_input_tokens`. Only `langfuse.trace.metadata.*` becomes Laminar metadata. In 6.x those values are JSON-encoded (`"\"acme\""`) and decoded; in 4.x / 5.x they are raw and kept as is, picked by the `langfuse-sdk` scope version. Decoding raw values too turned a 5.x string like `"12345"` or `"true"` into a number or boolean (Bugbot on #361).
- **Provider and request parameters:** Langfuse has no provider field (its cost inference matches the model name only). `gen_ai.system` comes only from LangChain's `ls_provider` observation metadata, with `LS_PROVIDER_ALIASES` for the values that differ from Laminar's price providers (`amazon_bedrock`, `google_vertexai`, `google_genai`). `@langfuse/openai` records none: the client may point at any OpenAI-compatible API. `langfuse.observation.model.parameters` maps to the `gen_ai.request.*` keys Laminar's instrumentations write (`reasoning_effort` → `gen_ai.request.reasoning.level`, the max-token names → `max_tokens`, `n` → semconv `choice.count`); other keys stay raw. `@langfuse/openai` JS records only a fixed key list: chat drops `reasoning_effort` / `max_completion_tokens` entirely, and Responses puts the response's `reasoning` into observation metadata, which maps to `gen_ai.response.reasoning.level` (the applied effort, a default when none was requested; named after the request key, as in lmnr-python's OpenAI Responses instrumentation). `@langfuse/langchain` records temperature, max_tokens, top_p and the penalties only. Python Langfuse records more (its OpenAI wrapper keeps `reasoning_effort`); lmnr-python shares the mapping table.
- **Converted attributes are dropped from Laminar's copy** (never from Langfuse's export), so Laminar doesn't store and bill each payload twice. A translation value of `undefined` (`Translated` in `translate.ts`) removes the key in `endMirror`. Dropped: `model.name`; `usage_details` / `cost_details` when they produced attributes; the input / output key the value came from (`observation.*`, else `trace.*`) whether it became GenAI messages or the raw `lmnr.span.input/output`; `model.parameters` is rewritten to only its unmapped keys (`verbosity`, `@langfuse/openai`'s `response_format: ""`, a second max-token name) and dropped when none are left. Metadata, tags, user / session ids and unconverted values stay. lmnr-python does the same, plus openinference's `llm.*` families on LiteLLM spans.
- **Errors:** Langfuse never records exception events. A throw in `startActiveObservation` sets the OTel status to ERROR. A throw in `observe()` leaves the status UNSET and sets `langfuse.observation.level=ERROR` + `status_message`. Either case gets a synthesized `exception` event on Laminar's copy only, because the event is the one thing that marks a span failed in Laminar.
- **Version quirks:** the bridge version is the span's instrumentation scope version, i.e. Langfuse's `LANGFUSE_SDK_VERSION` constant, which lags the package in some releases (4.6.1 reports `4.6.0`). `@langfuse/langchain` 4.x records no tool definitions at all.
- **Tests:** no extra CI job (same pattern as openrouter's `@openrouter/sdk-legacy`). devDeps pin `@langfuse/*` 6.x exactly, plus exact `npm:` aliases of the latest 4.x and 5.x (`@langfuse/{core,tracing,otel,openai,langchain}-v4` / `-v5`). The suite lives in `test/langfuse-bridge/suite.ts` (`langfuseBridgeSuite(sdk)` takes the five modules and the major) and runs from `langfuse-bridge.test.ts` (6.x, plus the SDK-independent translation / instrumentation tests), `langfuse-bridge-v5.test.ts` and `langfuse-bridge-v4.test.ts`. node:test runs each file in its own process, so the majors never share Langfuse's or OTel's global state. Suite code may only use APIs all three majors have (`propagateAttributes` from `@langfuse/core`, no `updateActiveTrace`); it asserts the spans' scope major equals `sdk.major`, so a run can't silently fall back to 6.x.
  - The aliased `@langfuse/openai` / `langchain` depend (not peer) on `@langfuse/tracing` of their own major, so each set resolves consistently. The suite imports the 6.x packages only as types, so the v4/v5 files run exactly what a 4.x / 5.x app has.
  - `LangfuseSdk` is typed against 6.x, so the v4/v5 files pass their modules `as unknown as LangfuseSdk`: older majors' classes are distinct types (protected members, `metadata: Record<string, string>`) and fail `tsc`. The root `pnpm build` runs `pnpm typecheck` over `test/` first (CI's "Build package"), so `pnpm -r build` alone won't catch that.
  - Adding any dep re-resolves the `ai-v5` / `ai-v6` dist-tag aliases in the lockfile, even with `--offline`; that churn is expected.
- **Out of scope:** AI SDK spans that only flow through `LangfuseSpanProcessor` (never through the `langfuse-sdk` tracer), the legacy `langfuse` npm package, and apps with no OTel provider (Langfuse's spans are non-recording, so there is nothing to mirror).
