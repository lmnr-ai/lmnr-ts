# Pi Durable (`@earendil-works/pi-durable`) — LAM-2457

- **Two halves, one per concern.** `PiDurableTracer` (`telemetry.ts`) is the `TelemetryContext` passed to `Harness.open({ telemetry })`: it owns run identity, propagation and run end. The extension (`index.ts`, plain `{ name, hooks: [{ task: "pi.generation" | "pi.tool", handlers }] }` objects, so no runtime import of pi-durable) records LLM and TOOL spans. Hooks find their adapter through `context.telemetry`, which is the phase's `PiSpan`; without our telemetry they warn once and do nothing.
- **Pi's spans are never exported.** A `PiSpan` only carries its run's anchor (trace id, a pre-chosen root span id, the submit time). `inject` returns that anchor as `traceparent` + `lmnr-pi-run-start`, whatever Pi span it is called on, so the carrier Pi stores on every submission and task always names the run root.
- **Every Laminar span is synthesized when its work ends**, with an explicit start time: LLM at `afterResponse`, TOOL at `afterTool`, the root at settlement. The root is created last and gets the anchor's ids stamped over the SDK's (the Mastra pattern: `Object.assign(span.spanContext(), …)` + `dropPathInfo`). Children set `PARENT_SPAN_PATH` / `PARENT_SPAN_IDS_PATH` in their start attributes, because the root is never a live span in the processor's cache. This is what makes restarts work: whichever process sees the settlement exports the one root.
- **Verified restart behaviour (pi-durable 1.5):** after `close()` + reopen, a replay-safe tool task resumes in its `execute` phase with `resumed: true`, extracts the original carrier, and runs `afterTool` WITHOUT a new `beforeTool`. TOOL spans therefore start at the resumed phase's start when there is no pending entry. A request cut off by the close is sent again, through `beforeRequest`. Spans whose start hook ran in a process that died are dropped, never exported half-done.
- **Run end = the `pi.durable.submission` event, handled synchronously**, on a `pi.generation` phase (or a continue's submit span). `Submission.wait()` resolves at that commit, before the phase callback returns, so ending the root when the phase span settles lost it for hosts that flush right after `wait()` (the tests caught this). Only settlements that are `unanswered` or carry `answer.entry_id` end a run (placed writes settle `done` without one), and when the submit span reported `submission.id` in this process, only the run's own inputs. The failure text comes from the newest model error, since the phase's error status is set after the event.
- **Don't read `pi.live` from hooks.** `api.snapshot()` needs a doc token whose version matches the stored one, and `pi.live` is at v3 (a v1 token throws "newer version"). `pi.provider` is v1, and is read once per run with a structural token for the default session id (Sentry does the same); a failure only loses the default.
- **The system prompt and tools ARE visible to hooks**: pi-ai 1.x messages carry `role: "system"` entries (`content`, named `sections`, `toolsAdded` / `toolsRemoved`). `messages.ts` replays them like pi-ai's `getCurrentSystemPrompt` / `getCurrentTools`. The `systemPrompt` option only overrides.
- **Double counting: suppress the generation PHASE, not `pi.ai.request`.** pi-ai's `pi.ai.request` callback just awaits a promise; the SDK call runs outside it, so suppressing there did nothing (checked with a faux response factory reading `isTracingSuppressed`). `runSpan` runs `pi.durable.phase` spans of `pi.generation` under `suppressTracing`. Our own spans pass explicit parent contexts, so they are unaffected. Other extensions' hooks in that phase are suppressed too.
- **Auto-instrumentation** wraps `Harness.open` (a plain object, shared by every importer of that copy) and returns `Object.create(options, { telemetry })`, keeping the host's getters. Pi reads options by property, never spreads them. It skips options whose telemetry is already a `PiDurableTracer` or any foreign telemetry, and installs the extension with `registry.install` (same name replaces). pi-durable is ESM-only (`exports` has only `import`), so the `require` hook never fires; `instrumentModules.piDurable` is the supported path.
- **Tests (`test/pi-durable.test.ts`)** load pi's packages with dynamic `import()` in `before()`: tsx runs the test as CJS, and `require` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED`. Restart is simulated with a `MemoryStorage` proxied so `close()` is a no-op, plus a second `laminarPiDurable()` so no memory carries over. pi-ai's faux provider always reports zero cost, so cost mapping is unit-tested.
- Adding pi-ai as a dev dep pulled a newer `@aws-sdk/client-bedrock-runtime`, and two copies broke `tsc` on the Bedrock instrumentation (`ClassBuilder` private `_init`). Keep the SDK's own dev dep on the same version.
