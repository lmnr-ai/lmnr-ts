# instrumentation/

## `LaminarInstrumentation` base class (`shared/base.ts`) — LAM-2436

- Every library instrumentation except the AI SDK (whose v7 telemetry integration is a different shape), Mastra (an exporter) and Temporal (interceptors) extends `LaminarInstrumentation`. It is the TS counterpart of Python's `BaseLaminarInstrumentor`, but not a 1:1 port. A subclass passes a short name to `super("openai", config)`, which yields the OTel name `@lmnr/<name>-instrumentation` and sets `this.traceContent`. Then it implements `modules()`: one `InstrumentedModule` per npm package, holding `name`, `supportedVersions`, `patch` / `unpatch`, optional `files` (package-internal hooks, used by LangChain), and `accepts`, which recognizes manual input. The base builds `init()` and a default `manuallyInstrument` from that list. Manual input can be an array, and input nothing `accepts` gets a `diag.warn`. LangChain overrides `manuallyInstrument` because its input is a bag of modules.
- **`modules()` runs inside the `InstrumentationBase` constructor** (`init()` is called from `super()`), before any subclass field is assigned. Only reference `this` lazily, inside the patch callbacks.
- **Patch methods with `this.wrapMethod(target, method, (patched) => wrapper)` / `this.unwrapMethod`, not shimmer's `_wrap`.** The original is stored in a non-enumerable, own-property record under `Symbol.for("lmnr.<instrumentationName>.patches")`. Re-patching only swaps `patched.instrumentation` to the newest instance, so a re-`initialize()` refreshes `traceContent` without double-wrapping. The same holds when two module definitions resolve to the same prototype (`@openai/agents` re-exports `@openai/agents-openai`'s model classes), so no `WeakSet` guard is needed. Wrappers read `patched.instrumentation.traceContent` at call time. Assignment goes through `setProperty`, which redefines getter-only or read-only-but-configurable properties (bundler-emitted CJS `exports`) the same way shimmer does.
- **Version stamping:** `instrumentation.startSpan(options, packageName?)` is `Laminar.startSpan` plus `lmnr.span.instrumentation_scope.name` (the npm package name, which defaults to the first module) and `.version`. All Laminar spans share one OTel tracer, so these attributes are what identify the wrapped library. Wrappers must create spans through it. Code with no instance at hand stamps by hand with `span.setAttributes(instrumentationScopeAttributes(pkg))`: the LangChain handler, the openai-agents processor, `instrumentClaudeAgentQuery` and the AI SDK v7 integration. The same applies to instrumentations outside the base class:
  - Temporal uses `@temporalio/client` for workflow spans and `@temporalio/worker` for activity spans.
  - Mastra uses `@mastra/core`, set in `buildLaminarAttributes`.
  - Stagehand v2/v3 use `@browserbasehq/stagehand` for their `Stagehand` parent span.
- **Spans built with `observe()` go through `instrumentedObserve(pkg)`**, a drop-in `observe` that stamps the span it opens. It reads `Laminar.getCurrentSpan()` as the first thing inside `fn`, so spans that user code opens inside are not attributed to the library. This is how kernel, Playwright (`playwright.page`), Puppeteer (`puppeteer.page`) and every Stagehand `laminarObserve` call (including the shared LLM-client wrapper) are stamped.
  - The browser instrumentations still extend `InstrumentationBase` directly. Their patch callbacks call `recordPackageVersion(pkg, moduleVersion)` themselves.
  - Puppeteer registers hooks for both `puppeteer` and `puppeteer-core`, and both patch the same browser classes. A page is therefore attributed to `puppeteer` when that package is installed, and to `puppeteer-core` otherwise. When the version can't be resolved, the version attribute is omitted rather than set to `"unknown"`.
- `shared/package-version.ts`: `getPackageVersion(name)` is cached per process. The auto-instrumentation hook calls `recordPackageVersion(name, moduleVersion)`, and require-in-the-middle reads that version from the exact copy being patched, so it wins. Manual instrumentation falls back to resolution:
  - it tries `require(name/package.json)` first;
  - **many SDKs (`@anthropic-ai/sdk`, `openai`) hide `package.json` behind their `exports` map**, so the fallback reads `<node_modules>/<name>/package.json` along `require.resolve.paths`;
  - this is done from the SDK's own location, then from `process.cwd()`.
  - Both builds have `require`: the ESM bundle gets rolldown's `createRequire(import.meta.url)` shim.

## Shared helpers (`shared/utils.ts`, `src/utils.ts`) — LAM-2440

- **Serialize span JSON with `toJson` / `toJsonOrString` from `src/utils.ts`, never bare `JSON.stringify`.** `toJson` never throws. It returns `undefined` for `null`, `undefined`, values JSON can't represent, and values whose serialization throws (a throwing getter or `toJSON`), so pair it with `safeSetAttribute` and the attribute is skipped. Bigints become strings and a `Map` becomes its entries. Only an object that is its own ancestor becomes `"[Circular reference]"`: the replacer tracks the path from the root through `this`, so it must stay a `function`, not an arrow. A "seen anywhere" set also replaced the second copy of a shared object (LangChain shares tool-call args between `tool_calls` and content blocks). `toJsonOrString` returns strings as they are (the old Mastra / AI SDK v7 `serializeJSON` behaviour). Leave `JSON.stringify` where the bytes are hashed or parsed back: the AI SDK replay path (`stringifyPromptForTelemetry`, `base-language-model.ts`), Temporal headers, and serialized span contexts.
- **`recordSpanError(span, error)` is the only way to mark a span failed.** It sets `error.type` (the `Error` subclass name, else `"Error"`), records the `exception` event, and sets ERROR with the message. In Laminar, `setStatus(ERROR)` alone does not mark a span failed; the `exception` event does. `toError` gives non-`Error` values a message from their `message` field, the string itself, or their JSON. `finishSpan(span, error?)` is that plus OK-or-ERROR plus `end()`.
- **`Laminar.withSpan` records the exception of a throw or a rejected promise itself**, and it chains `.catch().finally()` onto a returned promise. That chaining drops `APIPromise` / `HttpResponsePromise` helpers. A wrapper that also records the error in its own `catch` therefore records it twice, and the old openrouter / google-genai / aiplatform wrappers did. Wrappers run the SDK call through `callWithSpan(span, call)`, which boxes both the result and a thrown error past `withSpan`: the span is active, nothing is recorded, and the result comes back untouched. Also use it to activate a PARENT span around a child: an outer `withSpan(parent, ...)` records a tool's error on the parent and marks it failed.
- **`traceCall(span, call, onSuccess)` is the standard wrapper body.** A throw or rejection goes to `finishSpan(span, error)`. `onSuccess(data)` runs once, owns ending the span (right away, or from a stream's `onDone`), and its return value replaces the data. If it throws, the span is ended and the data handed back. `settle` keeps the promise type: `APIPromise` through `_thenUnwrap` (with `fail` on `_responseProps()` / `responsePromise`), `HttpResponsePromise` through `constructor.fromPromise(withRawResponse().then(...))`, any other thenable through `.then`. Typesafe is the exception: it records from `asResponse()` and returns the promise untouched.
- **Streams:** `instrumentStream(stream, { onEvent, onDone })` instruments an SDK stream object in place. It wraps the `iterator` instance field when present (openai and anthropic `Stream`, where `[Symbol.asyncIterator]()` and `tee()` both call it), else replaces `[Symbol.asyncIterator]` (cohere, openrouter). For an async generator, which a caller may drive with `next()` directly, use `traceAsyncIterable`, which returns a new generator (google-genai). In both, `onDone` runs exactly once (completion, error, or early `break`), and hook errors are swallowed via `safely`. A failing attribute extractor must never surface in the caller's `for await`; the old google-genai wrapper rethrew it.
- `safeSetAttribute` skips `null` / `undefined` / `""` / `[]`. The GenAI content keys are `GEN_AI_INPUT_MESSAGES` / `GEN_AI_OUTPUT_MESSAGES` / `GEN_AI_TOOL_DEFINITIONS` in `tracing/attributes.ts`. `parseJson` (`src/utils.ts`) is `JSON.parse` that hands back the input on failure.

## General

- Instrumentations live under `src/opentelemetry-lib/instrumentation/<name>/` and are registered in `src/opentelemetry-lib/tracing/instrumentations.ts` (both auto-registration path and the `manuallyInitInstrumentations` path — keep the two in sync).
- For manual instrumentation, expose an option key on `InitializeOptions.instrumentModules` and wire it through `manuallyInitInstrumentations`.
- `@openai/agents` re-exports types and classes from `@openai/agents-core` and `@openai/agents-openai`. Import from `@openai/agents` to avoid adding `-core`/`-openai` as direct dependencies.
- `AsyncLocalStorage.run(value, fn)` restores the previous context as soon as `fn` returns — for async iterables/streams, wrap **each** `next()`/`return()`/`throw()` call in its own `.run()` so the context is visible across yields, not just at iterator creation.
- Any code that manually constructs a `ReadableSpan` (e.g. framework-exporter bridges that synthesize spans from non-OTel sources) MUST call `makeSpanOtelV2Compatible` from `../../tracing/compat` on the result — without it, setting only v2 fields (`parentSpanContext`, `instrumentationScope`) breaks users on OTel SDK v1 (parent-child links and scope info are dropped, traces render flat).

## OpenCode Instrumentation (`src/opentelemetry-lib/instrumentation/opencode.ts`)

- Trace continuity across the OpenCode subprocess boundary works by injecting a synthetic prompt part with `metadata.lmnrSpanContext` (a serialized `LaminarSpanContext`) in the patched `Session.prototype.prompt` / `promptAsync`. The OpenCode plugin (`@lmnr-ai/opencode-plugin`, separate repo `lmnr-ai/lmnr-opencode-plugin`) reads it from `chat.message`, strips it from `output.parts`, and creates the top-level `opencode turn` span with `parentSpanContext` set to that serialized context. The two halves run in different Node processes — there is no shared OTel context, only the on-the-wire prompt parts.
- Patching targets `Session.prototype.prompt` (and `promptAsync`), discovered by walking `OpencodeClient` → `instance.session.constructor`. `session` is a class field initialized in the constructor (not on the prototype), so `resolveSessionClass` MUST `new ClientClass()` to trigger field init before reading `instance.session.constructor`.
- The plugin lives in a separate repo and is fetched by OpenCode at runtime via `Npm.add` and cached under `~/.cache/opencode/packages/@lmnr-ai/opencode-plugin@latest/...` — opencode does NOT use the host project's `node_modules`. To test plugin changes locally, build the plugin and copy `dist/*` into that cache directory; reinstalling under `node_modules` has no effect on what opencode loads. The cache is only refreshed when the package version changes on npm, so a fresh `pnpm publish` is required for users to pick up plugin fixes (the SDK side and plugin ship independently).
