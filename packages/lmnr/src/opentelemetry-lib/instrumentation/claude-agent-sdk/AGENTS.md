# Claude Agent SDK instrumentation — settings.json outranks process env

- **Claude Code's settings `env` block wins over the subprocess environment.** Setting `params.options.env.ANTHROPIC_BASE_URL` is NOT sufficient to route the CLI through our proxy: a user with `ANTHROPIC_BASE_URL` in `~/.claude/settings.json` talks straight to their upstream and the proxy sees zero traffic, so the trace has only DEFAULT spans and no LLM span (lmnr-ai/lmnr#2167). Verified empirically against the bundled CLI: with the base URL in user settings, all requests went to the settings URL and none to the process-env URL. Same precedence applies to `ANTHROPIC_API_KEY`.
- **The fix is the flag-settings layer (`options.settings` → `--settings`), which outranks user, project, AND local settings.** `buildProxyFlagSettings` (proxy.ts) builds the object that the query wrapper (index.ts) assigns to `params.options.settings`. Verified end-to-end: 2/2 requests hit the proxy, 0 hit the upstream. The user's files on disk are NEVER modified.
- **Settings layers merge PER KEY, they do not replace wholesale.** Keys omitted from the flag layer keep their lower-layer value, so a redirecting key (`HTTP_PROXY` / `HTTPS_PROXY` / `ANTHROPIC_FOUNDRY_RESOURCE`) must be **blanked to `""`**, not deleted. Blank them when they are present in the settings layers, the flag layer, **or `process.env`** — the flag layer is the only place we can override a value for the subprocess, so a key that exists only in the real env still needs blanking there.
- **`ANTHROPIC_FOUNDRY_RESOURCE` must be blanked whenever the Foundry base URL is pinned, regardless of where the resource lives.** The CLI treats base URL and resource as mutually exclusive and **hard-fails** (`API Error: baseURL and resource are mutually exclusive`) when both are live — it does NOT silently prefer one. So a resource sitting only in `process.env` while Foundry is enabled via settings breaks the run outright. Two independent spots must agree: `buildProxyFlagSettings` blanks it in the flag layer, and `getEnvVarsToRemove` (which strips it from `options.env`) must read the settings layers too — it originally checked only `envDict`/`process.env`, so a settings-only `CLAUDE_CODE_USE_FOUNDRY` never triggered the strip. `getEnvVarsToRemove` therefore takes `cwd` as a second arg. Verified: a corporate `HTTPS_PROXY` in user settings captured every connection until it was blanked. That same merge behavior is what lets the user's own `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` survive while we rewrite only base URLs — do NOT copy the whole settings env into the flag layer.
- **`HTTP_PROXY` / `HTTPS_PROXY` must be handled in BOTH cases (`PROXY_ENV_KEYS`).** Claude Code reads the lowercase `http_proxy` / `https_proxy` too and PREFERS them. Verified against the bundled CLI: with a lowercase `https_proxy` in settings and only the uppercase key blanked in the flag layer, all 3 connections went to the corporate proxy and 0 to ours; blanking the lowercase key too flipped it to 2/0. The array backs the neutralized list, the upstream-settings exclusion list, `resolveTargetUrlFromEnv`'s steps 1–2 lookups, and `getEnvVarsToRemove` — keep all of them keyed off `PROXY_ENV_KEYS` rather than re-listing the uppercase pair.
- **`buildProxyFlagSettings` normalizes the caller's `options.settings` env through `settingsEnvBlock`, NOT a raw spread.** A caller can pass JSON booleans / numbers (`{ env: { CLAUDE_CODE_USE_FOUNDRY: true } }`), and those flow into `isTruthyEnv` — which lowercases the value — so an uncoerced `boolean` would throw and abort proxy setup. `isTruthyEnv` takes `unknown` and is defensively type-checked (non-string → only literal `true` counts) so no future caller can crash the proxy on a stray type. (TS has no snapshot/restore path for proxy vars, unlike Python — see the Python SDK's `claude_agent/AGENTS.md` note about keeping the snapshot key list keyed off `PROXY_ENV_KEYS`.)
- **Every provider-enabled check must go through the SAME truthiness helper.** The subprocess-env pin path in `index.ts` uses the exported `isProviderEnabledInEnv(env, useKey)` (a thin `isTruthyEnv` wrapper), NOT an inline `env.CLAUDE_CODE_USE_X === "1"`. When the two disagree, `getEnvVarsToRemove` (wide) strips `ANTHROPIC_FOUNDRY_RESOURCE` while the pin path (narrow) declines to write `ANTHROPIC_FOUNDRY_BASE_URL`, and `buildProxyFlagSettings` never sees `options.env` at all — so a Foundry setup that only sets `CLAUDE_CODE_USE_FOUNDRY=true` in `options.env` loses its only routing key and the CLI hard-fails with `Must provide one of the baseURL or resource arguments`. Verified against the bundled CLI. Python has always routed all three providers through `is_truthy_env`, so this asymmetry was TS-only.
- **`isTruthyEnv` accepts `1` / `true` / `yes` / `on`, case-insensitively — NOT just `"1"`.** Verified by probing the bundled CLI with `CLAUDE_CODE_USE_FOUNDRY` set to each value: `1`/`true`/`True`/`yes`/`on` all produce a Foundry-specific error (provider enabled), while `0`/`false`/`""` make a plain Anthropic call (disabled). This matters because the provider flag decides whether we pin a provider base URL: under the old `value === "1"` check, `CLAUDE_CODE_USE_FOUNDRY=true` + `ANTHROPIC_FOUNDRY_RESOURCE` blanked the resource (it is in `PROXY_NEUTRALIZED_ENV_KEYS`) without pinning `ANTHROPIC_FOUNDRY_BASE_URL`, stripping the only routing key and hard-failing the run. Note the debug-mode truthy set in `src/debug/config.ts` is a SEPARATE list that happens to match — do not consolidate them; they track different upstreams.
- **An empty string is NOT treated as unset for `ANTHROPIC_BASE_URL`** — writing `""` there does not fall back to the lower layer, it breaks auth. Only blank the redirecting keys above; always write a real proxy URL for the base URL.
- **Only pin provider base URLs that are actually in play — but key off the provider's ENABLING FLAG, not just its base-URL key.** `buildProxyFlagSettings` pins `ANTHROPIC_{BEDROCK,VERTEX,FOUNDRY}_BASE_URL` when `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY}` is truthy **or** the base-URL key is already set (see `PROVIDER_BASE_URL_ENV_KEYS`, which pairs each base URL with its flag). Keying only off the base-URL key is a bug: Foundry is commonly configured via `ANTHROPIC_FOUNDRY_RESOURCE` with **no** base-URL key, so the resource would get blanked (it's in `PROXY_NEUTRALIZED_ENV_KEYS`) while no proxy base URL was written — stripping its only routing key and breaking the call instead of intercepting it. Writing all provider URLs unconditionally is the opposite error (hands a Bedrock URL to someone who never enabled Bedrock). Pinned by the two `resource alone` / `only the enabling flag` tests.
- **`readClaudeSettingsEnv` MUST honor `options.settingSources`**, which gates which on-disk layers the CLI loads: `undefined` = all, an array = only those, `[]` = no filesystem settings at all. Verified against the real bundled CLI — a gateway in project settings got 2 requests with all layers loaded and 0 under `--setting-sources=user`. So reading a layer the CLI was told to ignore resolves an upstream the CLI never uses and points the proxy at an unintended host. The param threads through `resolveTargetUrlFromEnv`, `buildProxyFlagSettings`, `getEnvVarsToRemove`, and `createProxyInstance` — all four take it after `cwd`.
- **Upstream resolution MUST also read the caller's own `options.settings` (the flag layer), via `flagSettingsEnv`.** That layer outranks every on-disk layer inside the CLI, and `buildProxyFlagSettings` overwrites its base URLs with the proxy moments later — so a gateway or `CLAUDE_CODE_USE_*` provider config that lives ONLY in `options.settings` was silently dropped and the proxy forwarded to `api.anthropic.com`. Precedence in `resolveTargetUrlFromEnv` is `options.env` → `process.env` → **flag settings** → on-disk settings. `flagSettingsEnv` handles all three shapes (object / inline JSON / file path) and returns `{}` for anything unreadable, leaving the bail-out to `buildProxyFlagSettings`. The `settings` arg threads through `createProxyInstance` too.
- **`resolveTargetUrlFromEnv` reads settings LAST (after `options.env` and `process.env`) as the proxy's upstream.** Deliberately different from the CLI's own precedence: we want the most specific caller-supplied upstream for forwarding, while the CLI honors settings over process env — hence the separate flag-settings override. Pass `options.cwd` so project/local settings resolve against the session root.
- **`HTTP_PROXY` / `HTTPS_PROXY` are deliberately EXCLUDED from the settings fallback** (`UPSTREAM_SETTINGS_EXCLUDED_ENV_KEYS`). They are transport-level forward proxies, not Anthropic API bases, and they sit at the TOP of the resolution order (steps 1–2, above every base URL) precisely so our proxy forwards through a corporate proxy when the process env demands it. Reading them from settings too would mean a user with BOTH a gateway and a corporate proxy in `~/.claude/settings.json` resolves the upstream to the *proxy*, so intercepted API calls get forwarded to a CONNECT proxy as if it were an API host and fail. The `options.env` / `process.env` handling for these keys is unchanged (pre-existing behavior: a proxy var in the real env IS the target) — settings simply do not contribute them. Pinned by the three `shadow the gateway` / `only a proxy var` / `process-env proxy var` tests.
- **`createProxyInstance` must NOT re-resolve the upstream — the caller passes the already-resolved `targetUrl` (and `cwd`).** It used to call `resolveTargetUrlFromEnv(env)` itself with no cwd, so a gateway living only in project/local settings was missed when `options.cwd !== process.cwd()`: the proxy forwarded to the default Anthropic API while `ANTHROPIC_ORIGINAL_BASE_URL` pointed at the gateway. This mirrors Python, where `start_proxy(proxy, target_url=...)` has always taken the resolved value. Pinned by the `project-settings gateway when cwd differs` test (it fails if the resolution is moved back inside).
- **`options.settings` may be a `string` (JSON or a file path) or a `Settings` object.** Anything we cannot FULLY read must be left untouched (return `null`) so the CLI can still resolve it with its own cwd — replacing it with a proxy-only object would silently drop the user's real settings for that run. "Cannot read" covers more than a missing path: an unreadable file, malformed JSON (a trailing comma the CLI may tolerate), and valid JSON that isn't an object all count. This is why `loadSettingsFile` returns `Record | null` rather than defaulting to `{}`: `buildProxyFlagSettings` must NOT confuse a failed read with a valid-but-empty `{}` file (the latter still gets the proxy). The on-disk settings LAYERS want the opposite ("absent → `{}`", carry on), so `readClaudeSettingsEnv` applies `?? {}` at its single call site — do NOT reintroduce a wrapper function for that, and do NOT make `null` the same as `{}` inside the loader.
- This is a **cross-language parity surface** with the Python SDK's `claude_agent/{utils,wrappers}.py` (`build_proxy_flag_settings` / `read_claude_settings_env` / `apply_settings_proxy_override`). Keep the precedence rules and the neutralized-key list in sync.
- Test files must prefix `describe`/`it` with `void` (`void it("...", ...)`).
